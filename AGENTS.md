# Zenkai

Native, lightweight, open-source desktop spreadsheet in Rust + GPUI that opens, edits,
recalculates and saves `.xlsx` as close to Excel as possible. The calculation engine is
IronCalc, chosen in Phase 0 and vendored in `vendor/`; its calculation is never rewritten
from scratch. Phase 7 in `docs/SPEC.md` patches its cell storage and Zenkai's file I/O
for large files.

This file is the single source of truth for every agent and session working on this repo.
`CLAUDE.md` only points here. Rules, not prose.

## Documents

- `docs/SPEC.md`: the product spec. Scope of v0.1, architecture, budgets, phases.
- `DECISIONS.md`: every decision the spec does not cover, with date, options and reason. Local
  only: it is git-ignored, never commit it.
- `docs/IDEAS.md`: anything out of scope worth proposing. Never implement it.
- `docs/BENCHMARK.md`: Phase 0 engine report (does not exist until Phase 0).
- `docs/COMPATIBILITY.md`: generated by the compatibility corpus test (Phase 1).

## Priorities

When two conflict, the higher one wins:

1. **Reliability**: never lose or corrupt user data. Open + save without edits must leave
   the file equivalent in everything the app supports, and warn before losing anything else.
2. **Correct engine**: formula results match Excel.
3. **Smooth rendering**: the grid moves at 60 fps even with large files.
4. **Accessibility**: everything works from the keyboard, with Excel shortcuts.
5. **Features**: added only once the above is solid.

Design principle: reinvent nothing. Shortcuts, menu names, selection, formula error codes
(`#DIV/0!`, `#N/A`, ...) and layout copy Excel. An Excel user must need to learn nothing.

## Process

- Work advances by the phases in `docs/SPEC.md`. At the end of each phase: stop, report
  what was done, what is pending and the risks, and wait for approval.
- A decision the spec does not cover: choose the option closest to how Excel behaves and
  record it in `DECISIONS.md`.
- No functionality outside the spec, even if it is easy. Propose it in `docs/IDEAS.md`.
- Before closing a phase: `cargo fmt`, `cargo clippy` with no warnings, every test green,
  benchmark without regressions.
- If an engine or GPUI limitation blocks a requirement: stop and report it with
  alternatives. Never work around it silently.
- Keep `README.md` current with how to build, test and run the benchmark on Windows.

## Architecture

- Cargo workspace: `crates/engine`, `crates/formats`, `crates/grid`, `crates/app`, `bench/`,
  plus `crates/agent` and `crates/mcp-relay` for Phase 6.
- `agent` (settings, agent tools, MCP bridge) uses `engine` and `types`, never GPUI;
  `app` uses `agent`; `grid` knows neither. `mcp-relay` (the `zenkai-mcp` binary) is
  standalone and depends on no Zenkai crate.
- Dependencies flow one way: `app` uses `grid`, `engine` and `formats`; `grid` does not
  know the engine; only `engine` knows IronCalc or logisheets. Where `formats` sits
  relative to `engine` is decided in Phase 1 and recorded in `DECISIONS.md`.
- `engine` exposes the `Engine` trait (load, save, read range, write cell, undo, redo,
  sheets). It is the only crate that depends on the engine library.
- `grid` is a custom GPUI element. It draws only visible cells and reads from a cache of
  the visible range (formatted values and styles), never from the engine per frame. The
  engine reports which cells changed; only those are invalidated.
- The UI thread never blocks. Load, save and recalcs longer than a frame run in the
  background with a progress indicator.
- Per-frame work is proportional to what is visible, never to file size.
- If the engine model cannot cross threads, wrap it in a dedicated thread fed by a channel
  and record it in `DECISIONS.md`.
- Format layer: one read/write adapter per format behind a common interface. v0.1: xlsx
  (through the engine), csv and tsv (own code). Read-only fallback through `calamine`.

## Code guidelines

Code must be readable and maintainable by one person two years from now: simple, explicit,
no layers that are not justified today.

### Structure and limits

- One module per responsibility. A file past ~400 lines probably mixes two things.
- The only anticipated abstraction allowed is the `Engine` trait. Elsewhere: no traits
  with a single implementation, no wrappers that only forward calls, no just-in-case
  generics.

### Types

- Newtypes for domain concepts: `CellRef`, `SheetId`, `RowIdx`, `ColIdx`, `Range`. Never
  pass addresses as `String` or rows and columns as bare `usize`.
- Enums instead of booleans or strings for states and modes.
- Make invalid states unrepresentable with the type instead of validating them at every use.

### Errors

- `thiserror` in library crates, errors typed by domain; `anyhow` only in `app`, at the
  UI edge.
- No `unwrap()`, `expect()` or `panic!` in production code reachable by user data. Allowed
  in tests.
- Never discard a `Result` silently (`let _ =`, `.ok()` without handling the case). An
  error that cannot be handled is propagated with context or shown to the user.
- `#![forbid(unsafe_code)]` in every crate. If `unsafe` is ever needed, discuss it first
  and isolate it in one module.

### Concurrency and UI

- The UI thread never does I/O or long computation. Load, save and heavy recalcs go to the
  background and come back through the GPUI mechanism for that.
- Render reads data already prepared in memory. Never query the engine or the disk while
  drawing.
- Every app command is a GPUI action with a shortcut, so it works from the keyboard and
  appears in the command palette.

### Hygiene

- `cargo fmt` and `cargo clippy --all-targets -- -D warnings`, no exceptions. No
  `#[allow]` without a real reason.
- `tracing` for logs. Never `println!` or `dbg!` in committed code.
- No dead code, commented-out code or loose `TODO`s. Pending work goes to an issue or to
  `docs/IDEAS.md`.
- Minimal dependencies, with `cargo-deny` checking licenses and security advisories. GPUI
  and the engine pinned to a fixed version.
- Names per the Rust API Guidelines: `snake_case` functions, `CamelCase` types, no
  invented abbreviations.

### AI slop (rejected in review)

Defensive code for impossible states, generic functions used once, duplicated logic with
minimal variations, vague names (`data`, `handle`, `process`, `manager`), error handling
that returns a default value to hide a failure, and changes outside the scope of the task.

## Comments

No comments by default, including `///` doc comments. Names, types and structure must
explain what the code does.

Only these exceptions:

- An important implicit rule the code cannot express: an invariant, a mandatory call order,
  a guarantee another module depends on.
- A counterintuitive decision a reader would "fix" by mistake, for example deliberately
  replicating an Excel quirk.
- A workaround for a dependency bug, with the link to the issue.

When there is a comment: English, one or two lines, explaining why and never what.
Valid: `// Excel treats 1900 as a leap year; kept for date serial compatibility.`
Never comments that narrate the code, decorative section headers or commented-out code.

## Commits
- English, imperative, concise. Never a `Co-Authored-By` trailer.
- One commit per logical change. This is the rule agents break most often.
- Commit only what belongs to the task. Never someone else's untracked files.
- Subject line only by default. A two or three line body is justified only when the why
  is not visible in the diff: a subtle bug, a counterintuitive decision, a measurement
  behind the change.

## Branches
- Never commit to `main`. Every task starts on a new branch.
- One branch per feature or logical change. Group only changes that are related;
  never several unrelated features on one branch.
- Names: `feat/<topic>`, `fix/<topic>`, `perf/<topic>`, `test/<topic>`, `chore/<topic>`.
- Only the lead pushes and opens PRs, through scripts/pr; merging needs the user's explicit approval.

Good subjects: `Add atomic save with temp file swap`, `Fix range selection past frozen panes`,
`Cache visible range values in grid`. Bad: `Update files`, `Implement phase 2` (too big),
`Fixed bug in grid.` (past tense, vague, trailing period).

## Pull requests

Agents write the content; `scripts/pr` (bash, `gh`, `jq`) does the GitHub mechanics. Use
`--dry-run` to preview. All text is English and never contains the middle dot character.

- **Title:** `<type>: <imperative summary>`, type one of feat, fix, perf, chore, test, docs;
  at most 72 characters, no trailing period, ` (N/M)` appended for stacked PRs.
- **Body:** `## Why` (1 or 2 sentences), `## What` (2 to 5 bullets), `## Decisions`
  (optional: choice and reason), `## Validation` (tests, staging result, what was not
  verified), then `Card: <url>` and, when stacked, `Stacked on #N`. At most 40 lines.
  `scripts/pr/lint.sh` enforces it and `scripts/pr/open.sh` runs it before opening.
- **Review:** a summary of at most 6 lines and inline comments of at most 3 lines, each
  with an optional suggestion block. Low findings without action go only in the summary.
  A review is never an approval: it is REQUEST_CHANGES with a Critical, High or BLOCKER
  finding, otherwise COMMENT. Findings on lines outside the PR diff go into the review body.
- **Thread replies:** one line: `Fixed in <sha>.`, `Won't fix: <reason>` or
  `False positive: <reason>`.
- **Staging comment, one per PR:** gate result, measurements before and after, and what to
  test by hand.
- **Card:** every board card links its PR. `scripts/pr/open.sh --card <project-item-id>`
  appends `PR: <url>` to a draft card, or adds the PR to the project for an issue card.
  When the review closes, `scripts/pr/card.sh <project-item-id> <tldr-file>` appends a
  `TLDR:` of 2 or 3 lines to the card: what the review found and how it was resolved.
- `scripts/pr/test.sh` checks the scripts in dry-run against local fixtures.

## Validation

Builds are expensive, so they are batched: branches get cheap checks, the full gate runs
once per batch. Never run workspace-wide clippy or test, a release build or the
benchmark on a feature branch except for the single-branch case below.

Per branch, in its own worktree, for the crates it touches (`<crates>`):

```
cargo fmt
cargo check -p <crates> --all-targets
cargo test -p <crates>
```

Debug builds only. Parallel `cargo` invocations use at most `-j 8` in total.

A batch with a single branch runs the full gate directly in that branch's worktree and
copies the release exe from there; no staging branch is created.

A batch with several branches gets a fresh `staging/<date>` from `main` (adding `-n`
when the name is taken); the final tip of each branch is merged once with `--no-ff`. If
a branch changes after a failure, a new staging branch is created from `main` instead of
re-merging into the old one.

Full gate, once per batch, in this order:

```
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo deny check
cargo build --release
```

Plus the benchmark in `bench/` (release build) when the batch touches `crates/engine`,
`crates/grid`, `crates/formats` or `bench/`. Never draw performance conclusions from a
debug build. Nothing goes to the user with any of these red.

## Workflow

Branches are developed in parallel, one agent and one worktree each, and validated together
in a staging branch.

1. **Design.** A UI task gets a design artifact approved before implementation.
2. **Branch.** The implementer works per the code rules and runs the per-branch checks above.
   It commits in logical commits and never pushes.
   When the branch is ready for review, the lead pushes it and opens a draft PR with
   `scripts/pr/open.sh`.
3. **Static review, in parallel, no builds.** `quality-reviewer`, `security-reviewer` and
   `perf-auditor` read the diff against `AGENTS.md`, the security threat model and the
   `docs/SPEC.md` performance budgets. Fixes go on the branch as new commits.
   Each review and each fix round is posted on the PR (`scripts/pr/review.sh`,
   `scripts/pr/reply.sh`). The reviewers
   get the spec with decisions as plain statements, `AGENTS.md` and the diff: no reasons,
   no `DECISIONS.md`. The lead reconciles each finding against decisions.
4. **Staging.** `staging-integrator` (one agent, fresh context) validates the batch per
   Validation above: one branch is gated in its own worktree, several branches are merged
   one at a time with `--no-ff` into a fresh staging branch. After each merge it runs
   `cargo check --workspace --all-targets` to attribute breakage to a branch. Then, once,
   it runs the full gate. It copies the release exe to
   `C:\Users\giord\Desktop\zenkai-test\zenkai.exe`, overwriting; if the file is locked it
   reports it and never kills the process. Staging uses the persistent target dir
   `D:/More-Code-Projects/Zenkai-compiled/staging`, which is never cleaned. The result is
   commented on each PR of the batch.
5. **Failures.** A fix for one branch goes back to the owning branch and is validated in
   a new staging round. A fix caused only by the combination goes in its own `fix/<topic>`
   branch, never on staging.
6. **Manual test.** The user tests the exe by hand and approves the PRs. Agents never drive the GUI or
   send input to the desktop.
7. **Merge.** On the user's approval the lead merges the PRs into `main` one at a time,
   in staging order, with merge commits (`--no-ff`); then `git diff staging/<date> main`
   must be empty. Staging is never merged into `main`. The lead pushes `main` and the merged
   work branches (`feat/*`, `fix/*`, `chore/*`, `perf/*`, `test/*`) with the user's approval,
   so every branch is kept on GitHub. Muse never pushes; never push `staging/*`, `night/*`
   or `worktree-agent-*`. Never merge to `main` before the manual test.

Long commands run in the background and the agent waits for them; it never hands back early.
After two failed review rounds on a branch, stop and ask the user instead of iterating.

### Evidence that does not depend on a model's judgment

Agent review catches mechanical problems; it is not proof. Prefer objective checks, and
grow them with every bug found:

- Property tests and invariants for anything that can lose or corrupt data: undo/redo,
  open/edit/save/reopen, session close and restore, incremental versus full recalculation.
- Fuzz targets for every parser of untrusted input: xlsx, csv, session.json,
  settings.json, MCP messages.
- Mutation testing (`cargo mutants`) on changed modules, to check the tests would notice a
  broken implementation.
- Values computed by Excel and cached in the corpus files, compared with the engine.
- For changes to the engine, file I/O or the agent security boundary, a second review by a
  model of a family other than the implementer's, given only the spec, this file and the
  diff.
- Design judgment (UX, scope, trade-offs) stays with the user: manual testing of a build
  and the approved mockups in `docs/design/`.

## Agents and skills

- `.claude/agents/quality-reviewer.md`: blocking quality review, read-only.
- `.claude/agents/security-reviewer.md`: security review, threat model = a malicious file,
  read-only.
- `.claude/agents/perf-auditor.md`: static performance review on branches, benchmark in
  staging, read-only on code.
- `.claude/agents/test-engineer.md`: writes and runs tests.
- `.claude/agents/frontend-implementer.md`: implements UI in GPUI.
- `.claude/agents/engine-implementer.md`: implements engine work (Opus).
- `.claude/agents/implementer.md`: implements everything else: agent and MCP crates, CI.
- `.claude/agents/staging-integrator.md`: merges ready branches into `staging/<date>`, runs
  the full gate once and delivers the test exe.

Models: implementers and reviewers run on Sonnet, perf-auditor on Haiku, engine work on Opus.
Never delegate to the built-in general-purpose agent for implementation; it runs on the
session's model.
- `.claude/skills/review-changes/SKILL.md`: runs the reviewers in parallel and combines
  the verdict. It never fixes anything.
- `.agents/skills/zk-task/SKILL.md`: Muse workflow (`/zk-task`) turning a plain-words request into a TASK file on a fresh branch worktree, then stopping for approval.
- `.agents/skills/zk-branch/SKILL.md`: Muse workflow (`/zk-branch`) running a TASK file end to end: implement, branch checks, parallel reviews, fixes, REPORT.
- `.agents/skills/zk-staging/SKILL.md`: Muse workflow (`/zk-staging`) merging ready branches into `staging/<date>`, running the full gate and benchmark once, delivering the exe and report.

Each reviewer has a "Known false positives" section. It starts empty and grows with every
review that was wrong; that is how the system learns. Record them there, not in this file.
