# Zenkai

Native, lightweight, open-source desktop spreadsheet in Rust + GPUI that opens, edits,
recalculates and saves `.xlsx` as close to Excel as possible. The calculation engine is
IronCalc, chosen in Phase 0 and vendored in `vendor/`; its calculation is never rewritten
from scratch. Phase 7 in `docs/SPEC.md` patches its cell storage and Zenkai's file I/O
for large files.

This file is the single source of truth for every contributor, human or agent, working on
this repo. `CLAUDE.md` only points here. Rules, not prose. The maintainer's own workflow
(staging, PR mechanics, board, agent roster) is in `MAINTAINERS.md`.

## Documents

- `docs/SPEC.md`: the product spec. Scope of v0.1, architecture, budgets, phases.
- `docs/IDEAS.md`: anything out of scope worth proposing. Never implement it.
- `docs/BENCHMARK.md`: Phase 0 engine report (does not exist until Phase 0).
- `docs/COMPATIBILITY.md`: generated by the compatibility corpus test (Phase 1).

## Priorities

When two conflict, the higher one wins:

1. **Reliability**: never lose or corrupt user data. Open + save without edits must leave
   the file equivalent in everything the app supports, and warn before losing anything else.
2. **Correct engine**: formula results match Excel.
3. **Smooth rendering**: the grid moves at 60 fps even with large files.
4. **Accessibility**: everything works from the keyboard, with Excel shortcuts.
5. **Features**: added only once the above is solid.

Design principle: reinvent nothing. Shortcuts, menu names, selection, formula error codes
(`#DIV/0!`, `#N/A`, ...) and layout copy Excel. An Excel user must need to learn nothing.

## Process

- Work advances by the phases in `docs/SPEC.md`.
- A decision the spec does not cover: choose the option closest to how Excel behaves and
  record it in the PR's `## Decisions` section (the maintainer also keeps a local
  `DECISIONS.md`, see `MAINTAINERS.md`).
- No functionality outside the spec, even if it is easy. Propose it in `docs/IDEAS.md`.
- A UI task gets a design artifact approved before implementation.
- If an engine or GPUI limitation blocks a requirement: stop and report it with
  alternatives. Never work around it silently.
- Keep `docs/DEVELOPMENT.md` current with how to build, test and run the benchmark.

## Architecture

- Cargo workspace: `crates/engine`, `crates/formats`, `crates/grid`, `crates/app`, `bench/`,
  plus `crates/agent` and `crates/mcp-relay` for Phase 6.
- `agent` (settings, agent tools, MCP bridge) uses `engine` and `types`, never GPUI;
  `app` uses `agent`; `grid` knows neither. `mcp-relay` (the `zenkai-mcp` binary) is
  standalone and depends on no Zenkai crate.
- `pdf-host` holds the PDF wire format and client the `app` uses, plus the
  `zenkai-pdf-host` binary, the only code that loads pdfium. PDFs are read in that
  process so a pdfium crash never takes the app down.
- Dependencies flow one way: `app` uses `grid`, `engine` and `formats`; `grid` does not
  know the engine; only `engine` knows IronCalc or logisheets. Where `formats` sits
  relative to `engine` is decided in Phase 1 and recorded in the decisions log (`MAINTAINERS.md`).
- `engine` exposes the `Engine` trait (load, save, read range, write cell, undo, redo,
  sheets). It is the only crate that depends on the engine library.
- `grid` is a custom GPUI element. It draws only visible cells and reads from a cache of
  the visible range (formatted values and styles), never from the engine per frame. The
  engine reports which cells changed; only those are invalidated.
- The UI thread never blocks. Load, save and recalcs longer than a frame run in the
  background with a progress indicator.
- Per-frame work is proportional to what is visible, never to file size.
- If the engine model cannot cross threads, wrap it in a dedicated thread fed by a channel
  and record it in the decisions log (`MAINTAINERS.md`).
- Format layer: one read/write adapter per format behind a common interface. v0.1: xlsx
  (through the engine), csv and tsv (own code). Read-only fallback through `calamine`.

## Code guidelines

Code must be readable and maintainable by one person two years from now: simple, explicit,
no layers that are not justified today.

### Structure and limits

- One module per responsibility. A file past ~400 lines probably mixes two things.
- The only anticipated abstraction allowed is the `Engine` trait. Elsewhere: no traits
  with a single implementation, no wrappers that only forward calls, no just-in-case
  generics.

### Types

- Newtypes for domain concepts: `CellRef`, `SheetId`, `RowIdx`, `ColIdx`, `Range`. Never
  pass addresses as `String` or rows and columns as bare `usize`.
- Enums instead of booleans or strings for states and modes.
- Make invalid states unrepresentable with the type instead of validating them at every use.

### Errors

- `thiserror` in library crates, errors typed by domain; `anyhow` only in `app`, at the
  UI edge.
- No `unwrap()`, `expect()` or `panic!` in production code reachable by user data. Allowed
  in tests.
- Never discard a `Result` silently (`let _ =`, `.ok()` without handling the case). An
  error that cannot be handled is propagated with context or shown to the user.
- `#![forbid(unsafe_code)]` in every crate. If `unsafe` is ever needed, discuss it first
  and isolate it in one module.

### Concurrency and UI

- The UI thread never does I/O or long computation. Load, save and heavy recalcs go to the
  background and come back through the GPUI mechanism for that.
- Render reads data already prepared in memory. Never query the engine or the disk while
  drawing.
- Every app command is a GPUI action with a shortcut, so it works from the keyboard and
  appears in the command palette.

### Hygiene

- `cargo fmt` and `cargo clippy --all-targets -- -D warnings`, no exceptions. No
  `#[allow]` without a real reason.
- `tracing` for logs. Never `println!` or `dbg!` in committed code.
- No dead code, commented-out code or loose `TODO`s. Pending work goes to an issue or to
  `docs/IDEAS.md`.
- Minimal dependencies, with `cargo-deny` checking licenses and security advisories. GPUI
  and the engine pinned to a fixed version.
- Names per the Rust API Guidelines: `snake_case` functions, `CamelCase` types, no
  invented abbreviations.

### AI slop (rejected in review)

Defensive code for impossible states, generic functions used once, duplicated logic with
minimal variations, vague names (`data`, `handle`, `process`, `manager`), error handling
that returns a default value to hide a failure, and changes outside the scope of the task.

## Comments

No comments by default, including `///` doc comments. Names, types and structure must
explain what the code does.

Only these exceptions:

- An important implicit rule the code cannot express: an invariant, a mandatory call order,
  a guarantee another module depends on.
- A counterintuitive decision a reader would "fix" by mistake, for example deliberately
  replicating an Excel quirk.
- A workaround for a dependency bug, with the link to the issue.

When there is a comment: English, one or two lines, explaining why and never what.
Valid: `// Excel treats 1900 as a leap year; kept for date serial compatibility.`
Never comments that narrate the code, decorative section headers or commented-out code.

## Commits
- English, imperative, concise. Never a `Co-Authored-By` trailer.
- One commit per logical change. This is the rule agents break most often.
- Commit only what belongs to the task. Never someone else's untracked files.
- Subject line only by default. A two or three line body is justified only when the why
  is not visible in the diff: a subtle bug, a counterintuitive decision, a measurement
  behind the change.

## Branches
- Never commit to `main`. Every task starts on a new branch.
- One branch per feature or logical change. Group only changes that are related;
  never several unrelated features on one branch.
- Names: `feat/<topic>`, `fix/<topic>`, `perf/<topic>`, `test/<topic>`, `chore/<topic>`.
- Agents never push or open PRs; the human who owns the checkout does. Merging needs the
  maintainer's explicit approval.

Good subjects: `Add atomic save with temp file swap`, `Fix range selection past frozen panes`,
`Cache visible range values in grid`. Bad: `Update files`, `Implement phase 2` (too big),
`Fixed bug in grid.` (past tense, vague, trailing period).

## Pull requests

All text is English and never contains the middle dot character.

- **Title:** `<type>: <imperative summary>`, type one of feat, fix, perf, chore, test, docs;
  at most 72 characters, no trailing period, ` (N/M)` appended for stacked PRs.
- **Body:** `## Why` (1 or 2 sentences), `## What` (2 to 5 bullets), `## Decisions`
  (optional: choice and reason), `## Validation` (tests, CI result, what was not
  verified), and, when stacked, `Stacked on #N`. At most 40 lines.
  `scripts/pr/lint.sh` checks it.

## Validation

Run these on the crates you touch before opening a PR:

```
cargo fmt
cargo clippy -p <crates> --all-targets -- -D warnings
cargo test -p <crates>
```

GitHub CI (`ci.yml`) is the gate for every PR, forks included: it runs on Windows, Linux
and macOS. Staging is maintainer-only and not needed to contribute.

- No PR merges with a CI red caused by its own diff. A red unrelated to the diff is noted on
  the PR in one line, naming the branch that fixes it, and is never fixed inside that PR.
- One branch and one PR per concrete task; never mix tasks.

Full gate, the commands CI and the maintainer run in this order:

```
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test
cargo deny check
cargo build --release
cargo test --manifest-path vendor/<crate>/Cargo.toml
```

The workspace excludes the vendor crates, so the last line runs once for each one present
under `vendor/`: `ironcalc_base`, and `ironcalc` once it exists.

The benchmark in `bench/` (release build) matters when a change touches `crates/engine`,
`crates/grid`, `crates/formats` or `bench/`. Never draw performance conclusions from a
debug build.

## Evidence that does not depend on a model's judgment

Agent review catches mechanical problems; it is not proof. Prefer objective checks, and
grow them with every bug found:

- Property tests and invariants for anything that can lose or corrupt data: undo/redo,
  open/edit/save/reopen, session close and restore, incremental versus full recalculation.
- Fuzz targets for every parser of untrusted input: xlsx, csv, session.json,
  settings.json, MCP messages.
- Mutation testing (`cargo mutants`; the maintainer runs it in staging) on changed modules, to check the tests would notice a
  broken implementation.
- Values computed by Excel and cached in the corpus files, compared with the engine.
- For changes to the engine, file I/O or the agent security boundary, a second review by a
  model of a family other than the implementer's, given only the spec, this file and the
  diff.
- Design judgment (UX, scope, trade-offs) stays with the maintainer: manual testing of a build
  and the approved mockups in `docs/design/`.
